# 设计方案：WorkspacePreset

> 配套：[可行性评估.md](可行性评估.md)（宿主取证）、[实施与验收.md](实施与验收.md)（步骤与清单）。
> 本文给的是**可落地的设计**，不是最终代码；代码骨架只用来固定接口形状。

---

## 1. 一句话

**Host 半区挂在 `agent/created` 上，用「会话 cwd → 工作区 → 该工作区的 preset」这条
解析链覆盖默认值；客户端只在设置里提供一个按工作区选 preset 的表格。**
不做新 Remote 命名空间，不做新服务，不改内置包。

---

## 2. 职责切分

| 半区 | 做什么 | 不做什么 |
|---|---|---|
| Host（`lib/index.js`） | 读映射、判工作区、在创建/复用时切 preset、失败降级 | 不做 UI、不写自己的配置文件 |
| Client（`client.js`） | 设置页：列出工作区 × preset 下拉，写入 Config | 不判断会话、不调 `agentPresets.select` |
| Config（`lib/schema.js`） | 存「工作区 id → preset id」 | 不存默认值（默认值仍在 `agent-preset-registry`） |

**唯一的真源**：映射存本插件的 Config（进 profile 的 `cordis.patch.yml`）；
「没有映射时用哪个 preset」仍然由宿主的 `agentPresets.defaultId` 决定。
插件**不复制**宿主默认值，避免两份值打架（《踩坑录》§2.3）。

## 3. Host 半区

### 3.1 挂载点与顺序

```
apply(ctx)
  └─ ctx.inject(['agentPresets', 'workspaceRegistry', 'sessionProjections'], child => {
        child.on('agent/created', handler)     // serial，被 await
     })
```

为什么是 `agent/created` 而不是别的：

| 候选 | 判定 |
|---|---|
| `session/created` | 事件契约是 **`mode: emit`**（`void` 返回、不 await），在里面 `await select()` 拿不到任何顺序保证。而且此刻 agent 虽然已 `enter` 进注册表，但 `agent/created` 还没派发，生命周期状态属于"半发布"。`dsh-agent-loop:1748-1752` 的顺序是 `sessions.enter → agents.enter → sessions.announce → await agents.announce` |
| `agent/created` | ✅ agent 已登记、setup 已跑完、`source` 可区分创建/恢复；**且宿主会 await 完所有监听器才开始消费输入队列**（事件契约原文），所以切换一定能赶在第一个模型步之前 |
| `agent/pre-step` | 备选。也能赶在首步之前，但每轮都会进；`select` 在 `lastTurn > 0` 时本来就锁死，等于白跑，只是多一层开销 |

### 3.2 判定门禁（顺序即优先级，任一条命中就返回）

```js
// 伪代码，实际实现全包 try/catch
async function onAgentCreated({ agent, source }) {
  if (!config().enabled) return                      // G0 总开关
  const header = agent.session.header
  if (header.origin === 'subagent') return           // G1 子代理不碰
  if (header.parentSession !== undefined) return     // G2 分叉/种子会话继承父的语义
  if (header.cwd === undefined) return               // G3 无 cwd 无法判工作区

  const workspace = await resolveWorkspace(header.cwd)   // 见 3.3
  if (workspace === undefined) return                    // G4 不在任何工作区内
  const wanted = config().presetByWorkspace[workspace.id]
  if (wanted === undefined || wanted === '') return      // G5 没为该工作区配置

  const current = presets.composedPreset(agent.ctx)      // 见 3.4
  if (current === wanted) return                         // G6 已经是了

  if (source === 'resume' && !isBlank(agent.session)) return   // G7 老会话不回改
  await presets.select(agent, wanted)                    // 3.5
}
```

### 3.3 cwd → 工作区

```js
const workspaces = ctx.get('workspaceRegistry')
let ws
try { ws = await workspaces.resolveByPath(cwd) } catch { ws = undefined }  // 路径已不存在会 reject
```

**不要**用 `workspaces.list().find(w => w.sessionIds.includes(sessionId))`：
`attachSession` 发生在 `ensureSession` 返回**之后**（可行性评估 §2.2 `:701`），
`agent/created` 时刻拿不到。也不能用 `w.path === cwd` 的朴素字符串比较——`workspace.path`
是 `realpath` 规范化过的，`cwd` 是会话头里记的字符串，软链/大小写/8.3 短名会让比较失败。
`resolveByPath` 内部做的正是这套规范化，直接复用（《踩坑录》§5.4：平台语义要复刻，不要重新发明）。

> 失败降级：`resolveByPath` 抛错或返回 `undefined` → 当作"无映射"，交回宿主默认。

### 3.4 当前 preset

`presets.composedPreset(agent.ctx)`（`dsh-agent-preset-registry:723-725`，读 setup 阶段
`mount` 建立的 scope 绑定）。拿不到就视为不同，让 `select` 自己去判断是否可以切。

不要读 `sessionProjections.stateOf(session,'agentPreset')` 做比较：那个投影是
**日志里的已提交值**，在 `select` 成功前不会变，用来判断"要不要切"会得出"永远不用切"。

### 3.5 切换动作

```js
await presets.select(agent, wanted)
```

它在内部做三件事（`dsh-agent-preset-registry:753-771`）：

1. 串行化同一会话的切换（`this.switches`）
2. 查 `turnBoundary`：`openTurnStartSeq !== null || lastTurn > 0` → 抛 `agent-preset/locked`
3. `recompose(agent.ctx, wanted)` + `session.append('agent-preset/selected', …)`

**必须 try/catch**：`agent/created` 是 serial 事件，监听器抛错会让**会话创建失败**
并跳过后续监听器。这是本插件唯一的"能搞坏别人"的点。

**为什么必须在监听器里 await，而不是丢到 `setTimeout` 之后**：宿主在
`agents.announce()` 返回前不会放行该 agent 的输入队列（AgentLoop 侧 `publish()`
要 `await agents.announce(...)` 才返回）。丢到异步里就等于让第一条消息可能先进
模型——那正是"预设没生效"的观感。行号见 [取证索引.md](取证索引.md) #18/#20/#22。

### 3.6 空白会话复用（R1）

`source === 'resume'` 有两种来源：用户重开老会话（**不能碰**），和客户端
`reuseOrCreateBlank` 复用了工作区里的空白会话（**必须对齐**）。
判空白用投影，不要数事件：

```js
const b = ctx.sessionProjections.stateOf(agent.session, 'turnBoundary')
const blank = b !== undefined && b.lastTurn === 0 && b.openTurnStartSeq === null
```

`select` 自己也会拒绝非空白会话，所以这里多一层判断只是为了让日志干净、
避免每轮 resume 都撞一次 `agent-preset/locked`。

### 3.7 preset 不存在时

`resolve()` 会对未知 id 抛 `agent-preset/not-found`（`…:606-609`），错误里带
`available` 列表。处理：记 warn（**只记失败**，《踩坑录》§6.5），本轮不切，
会话按宿主默认创建。绝不能让配置里的一个过期 id 阻断创建。

## 4. 配置形态

### 4.1 采用：Config（volatile），不采用文件

```js
// lib/schema.js
import z from '@deepseek-ai/schemastery'

export const Config = z.object({
  enabled: z.boolean().default(true).volatile(),
  /** 工作区 id → preset id。键是 WorkspaceId，不是路径（见 4.3）。 */
  presetByWorkspace: z.dict(z.string()).default({}).volatile(),
})
```

三条理由：

1. **设置页要能改**：`dsh-settings` 只投影 `.volatile()` 字段，且**一个 volatile
   都没有的条目会被整条 `describe()` 丢弃**（`dsh-settings` 的 `volatileForm`
   返回 `undefined` → `describe()` 里 `return []`）。非 volatile 的写入路径还会被
   `isVolatilePath` 直接拒。精确行号见 [取证索引.md](取证索引.md) #36/#37。
2. **改了不用重启**：volatile 字段变更只 `updateVolatile` + emit，不重挂 fiber。
   代价是**每次现读**，不要缓存（《踩坑录》§2.2）。所以门禁里用 `config()` 取值，
   不在 `apply` 时算好。
3. **只有一套源**：不学"CLI 写 config.json + schema 带 `.default()`"那套混合
   （《踩坑录》§2.3），默认值会遮住文件，行为永远不生效。

### 4.2 dict 的可写性（R4 —— 实现前必须验证）

`isVolatilePath` 对 dict 的处理是：开头 `if (schema.meta.volatile) return true`，
所以**把 volatile 打在 dict 节点本身**，其下所有键都可写。
但这条推论依赖 schemastery 的 `z.dict(...).volatile()` 把 meta 放在 dict 节点上，
与 `volatileForm` 的 `schema.meta.volatile` 走同一分支 —— 需要在探针里
用一次真实写入确认（写入 `presetByWorkspace.<id>` 后 `form.getSnapshot().value` 能读到）。

**如果失败**，退到形态 B（不改设计，只改字段）：

```js
workspacePresetsJson: z.string().default('{}').volatile()   // 单字段，值为 JSON 文本
```

单字段的写入路径 `['workspacePresetsJson']` 一定在 volatile 之下，绝不可能被拒。
代价是客户端要自己 `JSON.parse` 和增量合并 —— 可以接受，因为读写都在本插件里。

### 4.3 键用 WorkspaceId，不用路径

| 方案 | 稳定性 | 问题 |
|---|---|---|
| 路径字符串 | 工作区删了再添加仍命中 | Windows 反斜杠进 YAML/JSON 的转义；大小写/软链/8.3 短名导致比较失败 |
| **WorkspaceId** | 工作区删除后 id 变，映射失效 | 无转义问题，`resolveByPath` 直接给出 id |

选 id。失效是**可接受**的（用户本来就把那个工作区从列表里移除了），且失效后果
只是回落到全局默认。文档里写清楚，别让后人以为是 bug。

## 5. 客户端半区

> 本节只到框架层（槽位、数据来源、界面形态）。**能照着写代码的实现设计**
> 见 [配置页实现设计.md](配置页实现设计.md)——那份是代码级的，含 `client.js` 完整骨架、
> 三条写入路径、六个边界与 API 形状核实表。

### 5.1 形状

一个 `settings.section` 页（不抢内置槽位）：

```
设置 → 新会话预设
┌───────────────────────────────────────────────┐
│ 默认（未单独设置的工作区）      [ 标准 ▾ ]     │  ← 只读展示，指明去哪改
│                                               │
│ D:\Program Code\plugins         [ 标准 ▾ ]     │
│ D:\agent\DeepseekHarness        [ 创造 ▾ ]     │
│ …                                             │
└───────────────────────────────────────────────┘
```

- 下拉里第一项是「跟随全局默认」，写入时 `unset` 该键（不是写空串）
- 不可用的 preset（`row.broken !== undefined`）灰显并显示原因
- 保存即生效，无"保存"按钮（《踩坑录》§7.3：`disabled` 的保存键会被当成 bug）

### 5.2 数据来源

| 数据 | 来源 |
|---|---|
| 工作区列表 | `ctx.remote.workspace.follow(signal)` 流（`namespace: 'workspace'`、`method: 'follow'`、`mode: 'stream'`），帧族 `baseline / upsert / remove / order / archived / pinned`。**不要**去读 `ctx.uiWorkspace` 或 `ctx.slots` 的 root hook store，那是别的插件的实现细节 |
| preset 列表 | `ctx.remote.agentPresets.list()` → `{ presets: [{id, name?, description?, broken?, isDefault}] }` |
| 当前映射 | `ctx.configForms.get(ENTRY_ID)` 的 `getSnapshot().value` |
| 写入 | `form.mutate([{ op: 'set', path: ['presetByWorkspace', wsId], value: presetId }])` / `[{op:'unset', …}]` |

> **注意** `dsh-client-ui-workspace:4142` 用的是 `ctx.slots.provideRoot({ hooks: { workspaces: … } })`，
> 那是**根级 hook**，注册进 `provideRoot` 的 hook 名必须全局唯一，且它是别的插件的
> 所有权范围。本插件要工作区列表就自己开 `workspace.follow` 流，别去蹭别人的 hook
> —— 蹭了会在对方卸载时把自己的设置页一起搞挂。

`mutate` 带 revision 比较（`dsh-client-ui-settings:1177-1194`），并发写会自己重读，
不用自己管。

### 5.3 两条《踩坑录》红线

1. **`apply` 必须同步**，禁止 `await $mount`（§3.1：会把挂载插进客户端启动序列，
   导致"新会话能开、消息发不出"）。本插件不挂新 Remote，天然满足；但**也不要**
   在 `apply` 里 `await` 任何列表读取。
2. **不要 `import '@deepseek-ai/dsh-client-ui-primitives'`**（§3.2：静态 bundle 不允许）。
   控件自己写，颜色只用 `--dsw-alias-*` token。

## 6. 与既有插件的边界

启动器里已经装了 `dsh-auto-review-custom`，它也在 `session/created` 里改**权限预设**。
两者改的是不同东西（权限旋钮 vs agent 组合），不会互相覆盖。但要注意：

- 它读的是 `permissionPresets`，本插件读 `agentPresets`，不要混
- 都在"新会话"上动手 → **测试时必须两个同时启用**，确认交叉场景（新会话 =
  auto 权限 + 该工作区的 agent preset）都成立
- 若将来两者都需要在 `agent/created` 上动手，注意 serial 事件的顺序与抛错传染

## 7. 明确不做的事

| 不做 | 原因 |
|---|---|
| 按工作区改**权限**预设 | 另一个能力（`permissionPresets`），需求没提；但骨架可复用 |
| 按工作区改默认模型 | `agentDefaultModel` 是全局单例，改动面更大，另立项目 |
| 新建工作区时弹窗问预设 | 打断首次使用流程；先做设置页，够用再说 |
| 改动/覆盖内置 preset 声明 | 与本需求无关，风险高 |
| 给客户端加新的 Remote 命名空间 | 现有 `agentPresets` / `workspace` / `settings` 三个命名空间已经够用（《踩坑录》§4 那四道坎一条都不用踩） |
