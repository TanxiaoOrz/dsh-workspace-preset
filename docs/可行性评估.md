# 可行性评估：按工作区设置新会话默认预设

> 取证基线：宿主 `0.2.0-rc.2`，取证对象是**当前实际安装并运行的那份构建**
> （`…\node_modules\.pnpm\@deepseek-ai+dsh-web-app@0._5455…\node_modules\@deepseek-ai\`），
> 不是仓库 HEAD。
>
> 下文所有 `文件:行号` 可复核，但**两个根目录别混**：

## 1. 结论

**可行。** 三条支撑事实：

1. 宿主 `session/create` 的协议入参**本来就有 `agentPreset`**，默认预设的解析点
   也在宿主侧，不在客户端：`agentPresets.resolve(id)` 在 `id === undefined` 时
   才回落 `defaultId`。
2. `agent/created` 是 **serial 且被 await** 的钩子，语义正好是「agent 已进入注册表、
   第一个模型步还没跑」；在这个窗口里切换预设是宿主自己支持的合法动作
   （`agentPresets.select` 会校验 `lastTurn === 0` 且无 open turn，成功后才把
   `agent-preset/selected` 写进会话日志）。
3. 工作区身份可以从会话 `cwd` 反查（`workspaceRegistry.resolveByPath` / `list()`），
   不依赖"会话已挂到工作区"这个**时序上更晚**的事实。

不需要自写 typert Remote，也不需要改任何内置包。

### 1.1 但要先接受一个结构性事实

**「新会话默认预设」不是一处配置，而是一个解析链**：

```
客户端点开工作区 → connectWorkspace → reuseOrCreateBlank
   ├─ 复用已有空白会话 → sessions.create({workspaceId, sessionId}) → 走 resume
   └─ 新建会话 → sessions.create({workspaceId})            → 走 create
                            ↓ Host sessionController.create
                  cwd = workspace.path ?? request.cwd ?? defaultCwd
                  agents.ensureSession(id, cwd, checkPersisted, request.agentPreset)
                            ↓
                  composeAgent(presetId) → agentPresets.resolve(presetId ?? defaultId)
                            ↓
                  agents.create / agents.resume(…, setup: mount(preset))
                            ↓
                  publish(): sessions.announce → agents.announce(source) → agent/created
```

两个必须正面处理的分支：**create 与 resume**。只处理 create 会让「复用空白会话」
这条最常见的路径漏掉。

## 2. 逐跳取证

### 2.1 默认预设在宿主侧解析，且可被显式覆盖

`dsh-agent-preset-registry/lib/index.js`：

| 位置 | 事实 |
|---|---|
| `:471-474` | `static Config = z.object({ default: z.string().required(), selectedDefault: z.string().volatile() })` |
| `:493-495` | `get defaultId() { return this.config.selectedDefault.get() ?? this.config.default }` |
| `:603-615` | `async resolve(id) { const wanted = id ?? this.defaultId; … }` —— **`id` 显式给定时完全绕开全局默认** |
| `:748-771` | `async select(agent, agentPreset)`：先查 `turnBoundary`，`openTurnStartSeq !== null \|\| lastTurn > 0` 就抛 `agent-preset/locked`；否则 `recompose` + `session.append('agent-preset/selected', …)` |
| `:592-598` | `remoteExportList()` 给每个 preset 标 `isDefault`，客户端的"默认"徽标就是它 |

### 2.2 `session/create` 协议层已支持 `agentPreset`

`dsh-api-session-controller/lib/typert.host.js:2116-2117`：

```ts
export interface SessionCreateRequest {
    readonly workspaceId?: WorkspaceId;
    readonly cwd?: string;
    readonly sessionId?: SessionId;
    readonly agentPreset?: string;      // ← 协议里就有
}
```

Host 实现在 `dsh-api-session-controller/lib/index.js`：

- `:686-714` `create(request)`：`workspaceId` 与 `cwd` 互斥 → `cwd = workspace?.path ?? request.cwd ?? defaultCwd`
  → `:697` `ensureSession(sessionId, cwd, request.sessionId !== undefined, request.agentPreset)`
  → `:701-708` **`workspace.attachSession(sessionId)` 在 `ensureSession` 返回之后**
- `:253-275` `ensureSession(...)`：`createOrAdopt` 去重 + `presetId` 不一致时
  `assertPresetUnchanged` 抛错 + cwd 不一致时 `ApiSessionCwdConflict`
- `:412-459` `createOrAdopt(...)`：
  - resume 分支 `:427-434` 用 **`storedPreset`**（会话日志里记的值），**忽略**传入的 `presetId`
  - create 分支 `:449-458` 用传入的 `presetId`（可为 undefined → 回落全局默认）
- `:358-371` `composeAgent(presetId)`：`presets.resolve(presetId)` → `setup: mount(agentCtx, resolvedId)`

**结论 A**：服务端能力齐全，`agentPreset` 是一个一等公民参数。

### 2.3 客户端这条链没有 `agentPreset`，也没有钩子

`dsh-api-session-controller/lib/client.js:2678-2687`：

```js
async create(opts = {}) {
  const shared = opts.sessionId === undefined ? {} : { sessionId: opts.sessionId };
  const payload = opts.workspaceId !== undefined
    ? { workspaceId: opts.workspaceId, ...shared }
    : { ...(opts.cwd === undefined ? {} : { cwd: opts.cwd }), ...shared };
  const result = await this.remote.session.create(payload);   // ← agentPreset 被丢掉
  …
}
```

调用方是 `dsh-client-ui-workspace/lib/client.js`：

- `:789-799` `connectWorkspace(id)` → `reuseOrCreateBlank(workspace)`
- `:800-809` `reuseOrCreateBlank`：**先找该工作区里已有的空白会话复用**
  （`summary.blank && summary.cwd === workspace.path && workspace.sessionIds.includes(id)`），
  找不到才 `this.sessions.create({ workspaceId })`
- `:810-820` `reuseBlank`：`sessions.create({ workspaceId, sessionId })`，
  `session/writer-held` 时回退成新建
- `:846-859` `startSession(workspaceId)`

**结论 B**：不能通过"让客户端多传一个参数"实现——那是内置包的内部调用，
插件拿不到这个接缝。必须在 Host 侧补。

### 2.4 切换时机：`agent/created` 是唯一干净的窗口

`…\@deepseek-ai+dsh-agent-loop_7e5ca28a…\lib\index.js:1744-1762`（`publish`）：

```js
detachSession = agent.ctx.sessions.enter(session);
detachAgent   = loopCtx.agents.enter(agent, parentAgent);
agent.ctx.sessions.announce(session);          // session/created（emit，不 await 返回值）
assertLive();
await loopCtx.agents.announce(agent, source, abort.signal);   // ← await
```

`…\@deepseek-ai+dsh-agent@0.2._c1d677a4…\lib\index.js:572-588` `announce`：`await this.ctx.serial(entry.carrier, 'agent/created', { agent, source, signal })`；
**监听器抛错会让创建失败并跳过后续监听器**（事件契约里写明，`agent/created` 是 `serial`）。
source 取值只有 `'startup' | 'resume' | 'clear' | 'compact'`；创建是 `'startup'`
（`:1799`、`:1867`），恢复是 `'resume'`（`:1970`）。

**结论 C**：在 `agent/created` 里 `await agentPresets.select(agent, id)` 是安全的，
但必须 try/catch 全包 —— 抛错会连累会话创建（与《踩坑录》骨架清单
「`apply` 全程 try/catch，绝不抛错」同理，只是这里对象是监听器）。

### 2.5 工作区归属：只能按 cwd 反查

`workspaceRegistry`（`dsh-workspace`）提供：

| 方法 | 用途 |
|---|---|
| `list(): Workspace[]` | 同步投影，`Workspace.path/sessionIds/title` |
| `resolveByPath(path): Promise<Workspace \| undefined>` | 按**规范化落盘路径**找，不创建 |
| `get(id)` | 按 id |

`Workspace.sessionIds` 在 `agent/created` 时刻**还不包含**当前会话（§2.2 `:701`
的 `attachSession` 在 `ensureSession` 之后），所以判工作区只能用 `cwd ↔ workspace.path`。

## 3. 被否掉的路线（以及为什么）

| 路线 | 否决理由 |
|---|---|
| **A. 让客户端 `sessions.create` 多传 `agentPreset`** | 客户端封包固化了 payload（§2.3），插件没有拦截点；改内置包 = fork 维护 |
| **B. 在设置里改 `agent-preset-registry` 的 `selectedDefault`** | 这是**全局**一个值（§2.1 `:493`），正是用户抱怨的现状；不能按工作区分身 |
| **C. 在 `session/created` 里切预设** | 该事件契约是 **`emit`**：宿主逐个调用回调、只 catch rejection，**不 await**，所以你在里面 `await select()` 拿不到任何顺序保证；而 `agent/created` 紧随其后（`sessions.announce → await agents.announce`），倒是被 await 的。另外 `AutoReviewCustom` 在 `session/created` 里切的是**权限预设**（`permissionPresets.set(session, …)`），那是会话级旋钮、不涉及 agent 组合重组，两者不可类比 |
| **D. 每个工作区各装一套 preset（bundle 级隔离）** | preset 是进程级注册表，重复 id 直接注册失败；且工作区是数据不是装配单元 |

> 方法论提醒（《踩坑录》§7.1）：上面四条不是"做不到"，而是"我知道的那条路走不通"。
> 真正让方案成立的是 §2.4 那个窗口，它一直都在，只是不显眼。

## 4. 剩下的真风险（按严重度）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **空白会话复用绕过"新建"** | 复用路径走 resume 分支，`storedPreset` 覆盖一切（§2.2 `:427-434`）。用户改了工作区默认值后，已存在的空白会话仍是旧预设 | 对 `source === 'resume'` 且**仍为空白**的会话也做一次对齐（判空白的方式见设计方案 §3.3） |
| R2 | **子代理/分叉会话被误伤** | `agent/created` 对子代理也触发，且 cwd 与父会话同工作区 | 用 `session.header.origin === 'subagent'` 与 `header.parentSession !== undefined` 跳过 |
| R3 | **覆盖了一个已被移除的 preset id** | `resolve()` 会抛 `agent-preset/not-found` | 解析失败 → 记 warn → 回落全局默认，绝不阻塞创建 |
| R4 | **dict 字段的写入路径可能被 `isVolatilePath` 拒绝** | `dsh-settings` 只放行 volatile 节点之下的路径，dict 内部键是否可写取决于 schema 形态 | 见设计方案 §4 的两种存储形态与 10 分钟探针 |
| R5 | **配置写盘会改写 patch 行** | `config-editor` 会把 `name` 改写成绝对 `file://` URL（《踩坑录》§2.4） | 不手改回去；文档写死「这是正常的」 |
| R6 | **改动要在 profile 里重新拷贝才生效** | 安装是目录拷贝不是软链（《踩坑录》§1.2） | 用哈希比对确认，别用肉眼 |

失败模式是**降级**而不是损坏：任何一个环节失败，行为都回到"全局统一默认"，
也就是用户现在的状态。

## 5. 验证这份评估的最小实验（实现前先做，30 分钟）

不要先写插件。先证明"宿主接受在创建后立刻改预设"：

1. 手写一个 30 行的探针插件，只做两件事：`apply` 里写文件探针；`agent/created`
   里 `console`/探针记录 `agent.id / source / cwd`，然后 `try { await agentPresets.select(agent, '标准 preset id') }`。
2. 挂进 profile → 打开一个工作区 → 看探针：是否 `source === 'startup'`、`select` 是否成功、
   新会话首轮工具表是否变成目标预设的。
3. **再打开同一个工作区**（此时会复用空白会话）→ 看 `source` 是否变成 `resume`、
   `select` 是否被 `agent-preset/locked` 拒绝。

第 3 步的结果直接决定 R1 的实现形态：如果 resume 时 `lastTurn === 0` 仍然可
`select`，那 R1 就退化成"同一段代码顺带覆盖"，成本几乎为零。

> 方法论（《踩坑录》§7.2）：这是能二分的那一步。别先读一堆源码再猜。
